# Product Surfaces

## 1. Consumer web

Public pages provide the brand, education, trust center, transparent pricing hypotheses, and a clear Check entry. Build Run 1 routes that entry through development sign-in so every persisted Check has a server-established person and household boundary. A later anonymous Check may be useful, but it must be ephemeral with no history under a server-minted anonymous context—never a client-supplied user ID. The authenticated member area adds history, orientation, household settings, and Trusted Circle. Search landing pages must be evidence-led and must not imply a current campaign feed until one exists.

## 2. Consumer mobile

iOS and Android are the primary recurring protection surfaces. The smallest durable loop is `share or paste → check → understand → act`. Native share integration is a Run 2 target unless it is actually implemented and device-tested; Build Run 1 establishes the Expo application, contracts, navigation, and Check flow.

## 3. Family experience

Family is a role-aware layer across web and mobile, not a separate surveillance dashboard. It covers protected members, invitations, consent, Trusted Circle, safe-word verification architecture, incident collaboration, orientation, and plan/seats.

## 4. BoomerBuddy HQ

HQ is a separate, denser employee surface over the same canonical platform. Initial modules are owner overview, customers/households, fraud evaluation/review, revenue pipeline, provider health, jobs, and audit. It does not replace accounting, payroll, mass email, or a full CRM.

## 5. Platform API and workers

The mobile, web, and HQ clients use typed contracts backed by one modular-monolith API. Transactional outbox events and background workers isolate follow-up work without introducing microservices. Partner APIs and co-branded enrollment are future consumers of the same authorization and entitlement model.

## Navigation constraint

Consumer navigation should expose only `Home`, `Check`, `History`, and `Family`; orientation appears as a guided task, not another permanent module. Recovery begins contextually from a result. HQ may be denser, but every module needs an accountable operational owner and a real workflow.
